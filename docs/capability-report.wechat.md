# 个人微信能力与验收状态

更新：2026-10-08。个人微信默认使用前台截图模式；企业后台收发需要经过验证的平台适配器。两种模式的验证结论分别记录。

## 个人微信前台模式

已实现单联系人流程：连接明确选定的单聊、建立历史基线、读取新文字、按模型和规则生成、保存 SQLite 发送记录、核对草稿、单次发送、核对外发回显。首次启动忽略历史消息；暂停和程序重启保留进度。用户必须明确点击启动，程序不会随启动自行启用回复。

微信窗口须完整位于主显示器并保持前台。切到其他应用时等待；回来后重新核对会话、消息连续性、配置和草稿。锁屏、睡眠、人工回复、草稿冲突、窗口实例变化和无法确认消息时暂停。

窗口辅助程序校验绑定的 HWND、PID、可执行路径、启动时间和窗口位置。辅助程序只能向绑定的前台微信输入无控制字符的 Unicode 文本，成对产生按下/松开事件，不操作剪贴板、不提供发送键命令。Electron 主进程在草稿全文和上下文再次验证后才按一次 Enter，并要求正确单聊的外发回显及空草稿。

发送结果不确定时保留记录、暂停并阻止重新启动，不重试发送。在微信人工核对后可明确标记结果；核对会重建后续接入起点，不自动重发原消息。近期列表会优先显示未核对记录，未知结果检查覆盖全部历史。

## 本轮证据

- 真实模型连接及图片读取返回 HTTP 200；项目已识别 Q 的新文字并生成回复。
- 实机发现最大化窗口边框越界、光标闪烁和旧输入组件重复首个中文字，已分别修复可见边界、精确像素等待和 Unicode 按下/松开输入。发送检查拦截了错误草稿，没有将其发出。
- 原生 Unicode 测试验证 Windows x64 结构布局、中文/英文/表情字符及非法输入拒绝；测试不操作真实桌面。
- 隔离流程使用实际驱动、实际 SQLite 和本地 HTTP 模型接口，验证生成、发送前持久化、回显、暂停/重启后续接、去重和未知结果人工核对。
- Windows 目录包、包内原生组件和实际 Electron 界面/IPC/SQLite 检查通过。测试使用隔离资料，不能代替微信真实发送证据。

**真实完整收发验收尚未通过。** 最近一次实机读取发现当前打开的是其他群聊，严格对象检查已停止，没有输入或发送。下一步是重新打开授权的 Q 单聊并保持前台，通过项目确认一条新回复的回显。没有使用助手手动发送代替自动流程。

真实验收使用 `npm run test:wechat -- --target "准确备注名" --current-chat`，只在用户已明确授权且已选定该聊天时运行。确认一条回复后自动暂停并退出。私有报告保存在 `.local/reports/personal-wechat`，不上传聊天原文、截图或密钥。

## 能力边界

个人模式依赖视觉读取，尚无原生账号、客户和消息 ID。单联系人一次验收不能证明所有联系人、长期连续运行、断网恢复、同名联系人区分或微信升级后的兼容性。群聊、语音、图片和文件不作为可自动回复的文字消息处理。

[批量模式](personal-wechat-batch.zh-CN.md) 作为展开功能保留，限明确填写的联系人名单。已验证合成容量和失败场景，尚未完成真实微信全列表覆盖和批量回复验收。

后台平台适配器当前没有证明未打开聊天的完整读取或不干扰办公的定向发送。登记设备和原生窗口元数据探测不提供这些能力，也不会解除运行门禁。企业状态见 [企业能力报告](capability-report.wework.md)。

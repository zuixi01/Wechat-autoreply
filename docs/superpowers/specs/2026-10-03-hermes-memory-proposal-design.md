# Hermes 学习机制接入工作记忆：需求与可行性

状态：分析提案。用户要求先理解需求、判断可行性、提供计划；本次不修改产品代码，也不启动学习或真实消息发送。

## 需求理解

让工作记忆形成持续学习循环：记录处理过程和人工纠正，提炼可复用经验，按场景调用，从实际反馈判断是否需要修订，保留有效方法并整理失效方法。用户不应每次都手动点击“从轨迹学习”。

这里的自我学习指记忆、处理方法和检索策略的迭代。当前方案不训练基础模型权重，也不让模型修改产品代码。业务效果需要真实案例验证，不能由“生成了更多经验”推断。

## 核对结果

2026-10-03 核对 Hermes 主分支提交 `1a4508e2aff2db5f50409893a2115be777bd5643`。后续实现固定此版本研究，避免主分支变动导致设计漂移。

Hermes 有小型持久记忆、历史会话检索、可编辑的过程性技能、后台复盘、技能整理与归档。后台复盘依赖其 Python Agent、模型运行时和工具管理，不能把单个 Python 文件直接复制到本项目就获得完整能力。本项目采用 TypeScript 适配这些机制；确实复制上游代码或提示词时保留对应 MIT 许可与归属。

本地代码核对：

- 当前产品入口仍使用 `ExperienceStore`、`induceCardsFromSession` 和 `memory:*` IPC。
- 卡片启用后统一注入；轨迹把本轮注入的卡片自动标为引用；发送结果参与 `used/success` 累加。
- 因而目前缺少可靠的场景检索、真实采用反馈、自动触发、版本发布与效果验证闭环。
- 工作区另有未接入产品链路的 `learning-*` 模块，覆盖 SQLite、修订、检索、队列、复盘及模型传输。它们是待复核的实现起点，不能算已交付功能。

## 推荐架构

在现有工作记忆中增加一个学习引擎，复用现有回复模型、知识库、轨迹、企业工作台和评测基础设施。没有必要把整个 Hermes 引入产品，也不增加 Python 服务。

闭环：问题片段 → 案例记录 → 空闲复盘 → 新建/修订候选 → 验证生效 → 场景检索 → 回复与员工反馈 → 再复盘。

四类资料分工：

1. 客户偏好：只在对应客户作用域使用，例如偏好短回复。
2. 处理经验：触发条件、做法、原因、例外，例如需求不完整时先补问型号和数量。
3. 过程技能：步骤、易错点和完成检查，例如报价、投诉、转人工的处理流程。
4. 历史案例：保留证据和反馈，供检索与复盘；案例中的客户原话不能提升为规则。

价格、库存、退款政策等业务事实继续由知识库提供；学习内容只指导处理方法。正式企业规则、发送权限、审核策略和收件人不由学习引擎更改。

## 数据与默认值

- `MemoryScope` 复用现有合同：workspaceId、platform、tenantId/accountId、conversationId。客户身份必须来自可信绑定，显示名不能作为身份。没有可信客户身份时不读写客户专属记忆，保留待绑定案例；可使用明确发布的账号通用经验。
- 本地 SQLite 保存个人学习；企业 PostgreSQL 保存企业正式学习资料，客户端不能自行发布企业规则。两者共享数据合同、检索文本处理、复盘输出及验证逻辑。
- `LearningEpisode` 是同一客户的一段问题处理过程，包含入站、草稿、人工修改、结果及反馈。全局引擎 session 可能跨客户，不能直接当学习单元。
- `MemoryRevision` 不可变；修改带 expectedRevision；候选版与生效版分离。`pending/active/stale/archived` 是管理状态；永久遗忘采用删除及最小禁止重学标记。
- `memoryEnabled` 控制调用记忆；学习模式 `off/suggest/auto` 单独控制产生和生效学习。默认 memoryEnabled=true、mode=suggest。off 停止学习和自动整理，已发布记忆仍可按 memoryEnabled 读取。
- suggest 自动提候选，人工使其生效；auto 只自动发布通过验证的低风险方法类修订。无验证依据、身份不清或涉及业务事实/权限变化时保留候选。
- 每轮最多 5 条生效记忆、最多 3 段相关历史案例，两者合计记忆上下文不超过 2000 tokens。没有匹配结果允许空上下文。优先使用匹配模型的 tokenizer；无法匹配时记录保守估算方式，不伪称精确消耗。
- 每轮固定 scope/corpusVersion/条目版本/内容哈希快照。生效内容或可检索集合变化会增加 corpusVersion；生成、缓存、审核绑定快照，发送前核对版本与有效期。
- 后台并发 1；默认空闲 15 秒后执行，单次超时 30 秒，输入上限 8000、输出上限 2000 tokens，每账号 UTC 日预算 50000 tokens，最多尝试 3 次。失败、取消或费用未知保留保守占额；删除案例不返还已消耗日预算。
- 案例默认保留 90 天，可配置；删除案例时处理证据依赖的候选和记忆。生效经验可长期保留，但无有效证据的条目不得自动更新。备份单独遵循保留期限，并在遗忘操作中明确覆盖范围。
- 默认每 7 天检查一次整理，空闲至少 2 小时才开始；14 天未使用标记待复核，30 天未使用允许归档，固定条目和人工规则不自动改动。新条目有 14 天宽限，未使用本身不证明无价值。合并先提候选，通过验证后归档旧项，保留来源与恢复能力。

## 反馈和验证

分别记录：加载、模型自报采用、员工采纳、实质修改、发送确认、事实错误、重复追问、越权承诺。发送确认不算业务成功，模型自报采用不算因果证明。

复盘必须支持“无值得保存的内容”。引用的案例必须属于输入作用域；修订只能针对已读取的准确版本；客户文本中的指令不能触发权限变更。结构校验、来源校验、事实与权限检查、代表性回放共同决定生效，不用单一模型自评分发布。

首次默认 suggest。auto 需要已校准的验证器和带人工期望结果的代表性回放：相关方法至少覆盖 5 条独立校准案例，无严重事实错误/越权/错误转人工放行，方法遵循和修改率不回退；证据不足继续 pending。这个最小检查数不等于统计意义上的效果证明。企业正式生效另须绑定原有评测准入与不可变发布。

严重负反馈暂停该版本并提修订；普通不采用不能直接认定经验错误。回滚生成一个恢复旧内容的新修订，保留历史。

## 完成标准

工程验收与业务效果验收分别记录，不能混称完成：

1. 自动产生学习任务、重启恢复、受预算约束；模型失败和学习取消不阻断正常回复。
2. 中文询价/投诉检索相关；数量和上下文有界；同名客户、企业、账号隔离。
3. 真实回复与界面显示实际加载的条目版本；旧快照或缓存不能在更新后复用。
4. 演示人工纠正 → 候选 V1 → 验证生效 → 使用反馈 → 候选 V2 → 回放 → 发布 → 回滚。
5. 界面支持学习模式、来源、差异、任务与费用、采纳/修改指标，以及固定、停用、归档、恢复、遗忘。
6. 老卡片有备份、幂等迁移；无法确定归属的卡片待整理；旧统计标为 legacy，不用于证明改善。
7. 整理可合并重复方法、归档过时方法、恢复被归档方法，且不改固定规则。
8. 本地与企业链路分别取得集成证据。企业变更重算发布指纹，进入原有评测/审核路径。
9. 工程测试、三套类型检查、构建、桌面演示通过；剩余缺口和故障明确记录。
10. 用真实人工标注做 A 无记忆 / B 旧卡片 / C 新机制对照，按完整客户会话分割学习/校准/留出集，冻结模型、知识、规则、记忆和检索版本，留出期间禁用学习。合成数据只证明工程行为。

建议业务起始目标：C 相比 B 的实质修改率相对降低至少 20%，严重事实错误/越权/应转人工却放行在验收样本中为 0，可处理覆盖下降不超过 5 个百分点，前台 p95 增量不超过 500ms（同设备同网络）。需报告会话级重采样区间；基线为零、样本不足或区间不支持结论时报告证据不足。以上是拟议目标，尚未得到用户确认，也不是已实现承诺。

首轮建议准备至少 100 条学习、100 条校准、200 条留出案例，留出至少 30 个独立会话，覆盖询价、投诉、转人工和多诉求；不足的类别单列，不能用总均值掩盖。案例数仅作起始检查，不保证统计功效。

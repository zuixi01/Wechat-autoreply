# 企业微信员工与外部客户私聊：技术路线核查

核查日期：2026-10-07。目标保持为多个员工在日常电脑办公，同时在员工原有外部客户私聊中自动回复。此次仅查公开文档和源码，没有运行第三方 SDK、登录网关或发送消息。

目前没有核实到可直接满足该目标的现成开源企微 SDK。已有可研究的桌面源码，以及需要供应商提供服务的协议网关示例；二者均不能凭 README 宣称后台共存、稳定收发已经可用。

## 官方能力的边界

| 能力 | 本次直接证据 | 对原需求的作用 |
| --- | --- | --- |
| 客户联系、企业群发 | 腾讯官方培训材料明确呈现“通知成员发送→群发确认”的操作流程 | 可用于客户经营任务，不能将该流程作为逐条即时自动回复的自由发送通道。当前开发者 API 页打不开，最新接口细节尚未直接复核。 |
| 会话内容存档 | 腾讯发布的功能条款将它定义为聊天场景数据备份接口能力 | 可以研究作为合规收集和历史输入来源；不能把存档服务当作发送 SDK。本次未核实到它提供员工身份的自由发送接口，也未获得当前许可、时延和完整消息字段证据。 |
| 微信客服 | 腾讯云官方发送文档使用微信客服渠道 ID、微信用户 ID，渠道类型为微信客服 | 能服务客服渠道中的用户，但不能替代员工既有客户好友私聊。 |
| 企业微信智能机器人 | 官方 `WecomTeam/aibot-node-sdk` 使用 `botId`、机器人 Secret、机器人消息回调和回复命令 | 官方源码完整，适合机器人会话；没有证据证明其可读取员工与外部好友的全部私聊，或作为该员工在原私聊自由发送。 |

一手依据：[腾讯广告群发培训，第14页](https://training.tencentads.com/uploads/202204/sWzeS5pX_qhcGo7.pdf)、[腾讯会话存档功能说明](https://market.cloud.tencent.com/marketplace/protocols/8076)、[腾讯云微信客服发送说明](https://cloud.tencent.com/document/product/269/110582)、[企微官方智能机器人 SDK](https://github.com/WecomTeam/aibot-node-sdk)。以上表格对通道适用性的结论是根据各通道身份和用途作出的工程判断；不宣称已遍历全部官方接口。

本次尝试的官方开发者页面 `92135`、`91774`、`91770`、`91360` 返回读取错误，没有采用非官方镜像的文字作为官方接口边界证明，也不据此断言以后不会出现新接口。

## 可进入实机评估的源码候选

`yangyuexiong/wx_work_auto` 有实际企微桌面自动化源码，可作为控件识别和发送适配的研究起点。作者列出 `3.1.10.x`、`4.1.39.x`，并指出 4.1 自绘控件可能缺少常见 UIA Patterns；这属于作者适配声明，尚未在用户电脑验证。[项目 README](https://github.com/yangyuexiong/wx_work_auto)

源码的窗口初始化会恢复窗口并获取焦点；发送通过名称搜索、键盘输入和回车。它没有在该实现中证明唯一客户寻址、持久消息 ID、历史游标及发送回显，也不能证明员工办公时无干扰。适合集成评估中的只读控件探测，不能直接成为生产后台发送实现。[main.py](https://github.com/yangyuexiong/wx_work_auto/blob/main/main.py)

实机评估应先记录用户实际企微版本及可读取的 UIA 控件，再检查：窗口被覆盖或最小化时能否读取；是否需要切换焦点；同名客户能否唯一绑定；重启、滚动和未读清除后能否完整续读。只要后台能力或唯一身份没有证据，保持自动发送能力关闭。

## 协议网关候选的真实状态

`lichaohuai/wecom-protocol-gateway` 公开仓库明确说明仅提供调用示例与能力清单，未提供网关服务地址、协议实现或部署服务端源码。其私聊寻址是 `S:uin`，发送携带 `device_id`；作者同时提示同一账号多设备会挤下线。因此目前只能作为供应商接口评估线索，用户没有对应服务，不能通过克隆仓库完成真实集成。与员工 PC 共存尚未核实。[仓库原文](https://github.com/lichaohuai/wecom-protocol-gateway)

示例收到回调后调用外部网关发送；没有消息 ID 去重、历史续拉或可靠发送回显流程。源码 `verify_signature` 在签名头缺失时也返回成功，即使已配置密钥，不能直接复用该验签实现。回调还在解析和处理之前确认成功，处理失败的补偿没有实现。[wecom_echo_bot.py](https://github.com/lichaohuai/wecom-protocol-gateway/blob/main/wecom_echo_bot.py)

后续若获得此类供应商 SDK，必须先拿到版本支持、原始消息 ID 与顺序、历史分页、账号/客户唯一 ID、员工人工发送识别、发送请求幂等与回显，以及同账号 PC 共存的可重复测试证据。当前这些证据均不完整。

## 新增供应商候选：WeChat-Work-Hook

截至本次核查，`xing653245/WeChat-Work-Hook` 主分支只有 README，没有公开 Hook 或 HTTP 服务源码。作者宣称采用 PC 进程注入，支持企微 `4.1.36.6012`、`5.0.3.6005`，要求版本匹配；消息发送示例是本地 `POST /api/message/text`，参数为实例 `port`、接收者 `user_id` 和 `msg`。完整接口文档需授权密码。上述均为供应商声明，尚未实机验证。[原仓库](https://github.com/xing653245/WeChat-Work-Hook)

已读到 [v2.2.3 发布说明](https://github.com/xing653245/WeChat-Work-Hook/releases/tag/v2.2.3)：2026-09-29 发布，提到连接线上授权服务及企微异常退出后自动恢复。未下载任何发布附件；发布页面存在不能证明接口行为、稳定性或安全性。

它可以进入供应商接口评估，不能作为现成开源 SDK 直接二开。员工原 PC 客户端是否能保持日常使用、操作时是否抢焦点、窗口覆盖和最小化时能否收发，以及原始消息 ID、历史补拉、人工发送识别、发送幂等与客户实际收到的回显，都没有公开证据。实际企微版本目前仍未知，不能直接判定兼容。

评估顺序：先只读确认实际企微版本；若候选匹配且后续获得授权文档，先核查消息与回显字段；再用明确测试员工和测试客户验收日常办公共存。当前继续保持该候选的自动发送能力关闭，不通过客户端降级、安装或注入来跳过验证。

## 当前开发选择

继续完成现有 Jev 决策、生成、复核和人工接管主线，同时保留平台适配层。企微优先做只读版本与控件探测，评估上述公开桌面源码的可复用部分；有合适且能共存的供应商 SDK 后再接入后台收发。官方存档可单独评估输入价值，但不能解决发送缺口。

离线模拟能够验证决策流程，不能证明企微实际收发、后台共存或业务准确度。若实机 UIA 只能靠抢焦点、名称搜索和回车发送，就仍未达到员工边办公边自动回复的原始目标，应继续寻找可靠通道，不能将前台方案标记为目标完成。

# 多客户会话采集开发与模拟验收

日期：2026-10-03。用户确认本轮覆盖微信和企业微信，先完成代码与模拟验收；本轮没有读取真实客户聊天或发送真实消息。

本轮解决的是“客户列表超出一屏后，如何发现并持续处理所有客户”的采集与调度问题。核心流程已接入主进程运行生命周期：按稳定客户 ID 分页发现会话，按持久化游标轮流读取消息，将消息与游标原子写入 SQLite，再交给现有审核与统一发送流程。屏幕中的名字、红点和坐标不作为客户身份或已处理证明。

## 已实现的行为

- 优先使用经过验证的语义读取器。UIA 接口在每次列表读取、消息读取前后核对登录身份，按稳定客户 ID 再确认目标。微信和企微独立声明客户端版本与能力。
- 列表分页和消息分页都有数量、大小、耗时上限。每次只处理有限页面，不一次性加载所有客户的聊天历史；客户目录支持最多 100,000 条合同内记录。
- SQLite v11 保存客户目录、活动版本、消息游标、读取状态和轮转顺序。消息与读取游标在同一事务提交；写库失败、迟到结果和旧版本结果不能推进游标。
- 消息提示触发增量读取；周期性重新检查会话列表，即使红点被清除、会话免打扰或提示遗漏，也会补读。未知客户提示触发目录补查，新增客户不取消其他客户任务。
- 重叠页面去重，列表排序或快照变化标记本轮不完整并等待补查。不能证明全量时不会显示检查完成；以前发现的客户不会因为一次扫描缺失被删除。
- 长历史按页面轮转。读取过程中持续收到提示的客户，也会让出下一次读取机会；每轮新消息分别计算读取预算。
- 未完成采集的会话不能发送。未变化的巡检保留模型任务及已完成草稿；新消息、身份变化、人工接管或暂停使旧任务失效。仅在统一发送器尚未记录任何执行且发生采集相关的临时拒绝时重新检查原草稿，已记录执行不重放。
- 每个账号的生成队列仍有 200 个内存任务上限。超载客户保留在账本并持久化转人工记录，不静默丢失；目录容量不等于可同时调用 100,000 个模型任务。
- 主进程报告列表覆盖状态、已发现数量、待读取数量和读取异常数量。界面明确提示“列表检查完成不代表消息全部处理完成”。暂停取消订阅、计时器和在途采集，迟到结果不能写库。

## 模拟验收标准与证据

独立场景 `tests/scenarios/multi-conversation.test.ts` 对两种平台分别建立 500 个客户，列表每页 40 个，包含同名客户、跨客户相同源消息 ID。每个平台再为底部客户追加一条消息，共计 1,002 条合成入站消息。

| 验收项 | 模拟要求 |
| --- | --- |
| 一屏以外客户覆盖 | 两种平台各发现 500 个稳定客户 ID，列表检查完成，待读取为 0 |
| 完整处理闭环 | 分页 UIA 接口 → 采集器 → SQLite → ReliableAgent → 合成审核 → 统一 Sender → 合成确认回执 |
| 遗漏与重复 | 两种平台各 501 条消息，501 次生成，501 次确认；重复巡检不追加生成或发送 |
| 物理执行串行 | 单账号模拟设备最大在途发送为 1；消息处理水位均持久化 |
| 暂停 | 停止后在途执行为 0，采集与队列计时器为 0 |

单元、集成和回归测试另外覆盖事务故障、重启游标、登录轮次隔离、跨客户读页拒绝、列表重排、重叠页、部分目录、无进展游标、读页超时、消息缺口、停止期间迟到结果、未变化巡检中的慢模型任务、生成与发送前检查的竞态、以及队列过载转人工。

## 真实客户端尚待验收

当前 C# 原生辅助进程仍只提供元数据探针，未实现并验证微信或企微的完整会话枚举和消息读取。`UiaCollectionSource` 是有身份复核的接口实现，测试使用合成读取器；生产 `RuntimePlatform` 尚未安装真实读取器和已验证发送适配器。因此，本轮代码与模拟通过后，真实客户端的自动回复仍保持能力未验证状态。

截图回退已提供独占列表、两行重叠滚动、快照变化检查的接口与算法，并通过合成视口测试；尚未接入真实滚轮执行器。该路径明确标记为前台操作和不完整覆盖，默认后台采集不会自动使用它。纯截图不能证明客户或消息的稳定 ID。

后续实机验收需分别提供两种客户端的专用测试账号、允许发送的测试联系人及客户端版本，验证列表虚拟化、稳定 ID、免打扰/离屏消息、员工操作冲突、锁屏/休眠、断网和升级兼容性。不能以某一种平台成功替代另一种。

去重承诺区分两种情况：同一运行期间未变化的重复采集不重新调用模型；确认发送的消息在重启后不重发。显式暂停或重启会使旧发送授权及建议失效，未处理消息需要重新审核，当前未提供跨运行的模型结果缓存。
